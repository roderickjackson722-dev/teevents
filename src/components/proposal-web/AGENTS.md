# Proposal web isolation
- Client proposal webpages use isolated capability-link documents and admin-only activity storage; admin Sent actions are status-only, and only an atomically claimed, Sent-gated client start choice sends the fixed-recipient notification with provider idempotency; never touch events, billing, or old proposal storage.
- Answers are deterministic extracts from the approved proposal content with section citations; unknown requests are saved for follow-up, not sent.
- Portal image slots map by label to approved screenshot asset pointers; unmatched labels stay named placeholders; reuse only the real founder portrait.
- The admin dashboard Proposals tab hosts this workspace; private management pricing lives in the validated document payload and uses a shared cents-based calculator, while public offers and historical copies without pricing retain their original content.
- Personalized Reason templates are editor-only starting points in `reasonTemplates`, inserted through the pure `withReason` helper; they never auto-fill, auto-send, or alter approved program terms.
- New documents snapshot their definition in the existing JSON payload; programDetails resolves terminology from that snapshot so overview and details agree while historical catalogs, legal terms and saved/sent wording remain unchanged.
- Proposal sections show unless listed in the payload's hiddenSections; sample-screen photos live in payload screens (defaults until saved) and admin uploads go to the existing admin-only event-images bucket under proposals/, so no schema change is needed.
- Program subsections in proposals can be hidden, renamed and reordered per program via the payload's programLayout; programSubsections is the single resolver for page and editor.
- Client acceptance requires a typed e-signature plus qualifying answers (shared acceptanceSchema); stored as a 'signature' activity row and included in the single fixed-recipient notification, so signing never creates events or charges.
- Editable selectionBoxes live in the existing document JSON and resolve server-side by ID; custom package/payment choices are signature-and-notification only, never checkout amounts, while documents without boxes retain their existing flow.
- References and Event Photo Links page order lives in the payload's extraPagesOrder, resolved by extraPagesOrder() for both page and editor; item lists reorder in place via moveItem.
- The full client-section order (everything after the fixed cover) lives in the payload's sectionOrder, resolved by proposalSectionOrder() for both page and editor; extraPagesOrder only seeds the references/photos positions when no sectionOrder is saved, so historical copies keep their layout.
